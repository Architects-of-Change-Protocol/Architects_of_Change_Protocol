# 02 — Threat Model

| Threat | Entry point | Control | Residual risk | Test |
|---|---|---|---|---|
| Revoked capability still honored at the API boundary | `POST /enforcement/evaluate`, `POST /execution/authorize` | `RevocationCheckPort` is a mandatory second argument to `evaluateEnforcement`/`authorizeExecution`; `runtime/api/routes.ts` resolves it server-side from the canonical capability-hash registry, never from client JSON | Only the capability-hash subsystem is wired | `runtime/api/__tests__/routesRevocation.test.ts` — "REGRESSION (was fail-open)" tests; empirically reproduced against pre-fix commit `71191de` (see `14-independent-review.md`) |
| **[P1, contained not fixed]** A second, HTTP-wired authorization path has no revocation check of any kind | `POST /data/access`, `POST /payout/execute` via `runtime/enforcement/enforceCapability.ts` → `protocol/consent/capability-authorize.ts` (`authorizeWithCapability`) | **Still none.** `validateCapabilityToken` checks only shape/hash/signature/expiry; no revoke mechanism exists for this `capability_id` key space. **Update (`15-final-hardening.md`)**: classified as (C) exported-but-currently-uncompilable, not live/productive. `createRuntimeServer`/`enforceCapabilityAccess` are no longer exported from `runtime/index.ts`'s stable surface — moved to `runtime/internal.ts` with an explicit security warning; `scripts/check-runtime-export-governance.mjs` now fails CI if they return to the stable surface. `authorizeWithCapability` itself carries a docblock warning. This reduces blast radius and discoverability risk; it does not add revocation checking, which remains out of scope | Building revocation for this token format is recommended as urgent next-sprint work, ahead of the persistent-datastore sprint if resourcing allows | Verified the new gate fails CI on regression (`15-final-hardening.md` §Part 2); see `14-independent-review.md` §Finding 1 for the original reproduction sketch |
| Client spoofs a fake "not revoked" signal | Any JSON body sent to `/enforcement/evaluate` | `isRevoked` is no longer a parsed field on `EnforcementRequest`/`ExecutionRequest` at all — the wire type does not accept it | None identified — a function literally cannot cross a JSON boundary, and the field is now absent from the parsed type | `runtime/api/__tests__/routesRevocation.test.ts` — "client-supplied isRevoked field ... is ignored" |
| Revocation registry throws / times out and the error is swallowed as "clean" | Any call to `evaluateConsentState`/`evaluateCapabilityState`/`evaluateEnforcement`/`authorizeExecution` | `createRegistryRevocationCheck` catches exceptions and non-boolean returns, mapping them to `unknown` (blocking), never to `false`/`null` | A future async/DB-backed registry needs its own timeout wiring; `withRevocationTimeout` is implemented and tested but not yet consumed by a production caller (none of today's registries are async) | `protocol/revocation/__tests__/revocationCheck.test.ts` — "FAIL-CLOSED REGRESSION" tests |
| Revocation check silently omitted by a new caller | Any new code path that wants to evaluate consent/capability/enforcement/execution state | `checkRevocation` is a required (non-optional) parameter at the TypeScript level — omitting it is a compile error, not a runtime default | A caller could still pass `ALWAYS_UNKNOWN_REVOCATION_CHECK` or a badly-implemented port that always returns `verified_not_revoked`; the type system cannot stop a deliberately wrong implementation | `scripts/check-revocation-fail-closed.mjs` Check 4 (structural backstop); code review is still required for new port implementations |
| Repeated/racing revoke calls produce inconsistent grant state | `ControlPlaneService.revokeGrant` | Idempotency-key cache + "already revoked returns the stable prior result" rule; the whole mutation is one synchronous block (no interleaving in Node's single-threaded event loop) | No real persistence — a process restart loses all grants and evidence; this is a known, documented limitation (see `06-cascade-design.md`) | `runtime/__tests__/controlPlaneRevocation.test.ts` — idempotency + concurrency suites |
| **[fixed in independent review]** A known idempotency_key replayed with a mismatched `subject_id` returns the cached (already-authorized) result without re-running subject validation | `ControlPlaneService.revokeGrant` | `fingerprintRevokeInput` now includes `subject_id`/`requester_id`, not just `grant_id`/`reason`, so a mismatched subject on a reused key is treated as a genuine conflict | Same in-memory-only caveat as above | `runtime/__tests__/controlPlaneRevocation.test.ts` — "REGRESSION FIX: same idempotency_key ... mismatched subject_id is a conflict" |
| **[fixed in independent review]** `/capability/mint` silently relied on an uncaught `TypeError` (undefined `checkConsentRevocation`) to fail closed, rather than a deliberate check | `POST /capability/mint` | `runtime/api/routes.ts` now explicitly wires `ALWAYS_UNKNOWN_REVOCATION_CHECK` (no real consent-revocation registry exists yet) instead of leaving the field unset | The endpoint is now *deliberately* always-denying rather than *accidentally* always-denying — it remains non-functional until a real consent-revocation store exists (next sprint) | `runtime/api/__tests__/routesRevocation.test.ts` — "/capability/mint deterministically denies" |
| Billing/entitlement state blocks a security containment action | `/access/grant/revoke` | `ControlPlaneService` has zero imports from `runtime/usage`/`runtime/monetization`; `CONTAINMENT_ENDPOINTS` is asserted absent from `DEFAULT_PRICING_RULES` by a CI gate | If a future PR wires metering into this route without reading this doc, the CI gate (`check:revocation-safety`) fails the build before merge | `runtime/api/__tests__/routesRevocation.test.ts` "billing safety override"; `scripts/check-revocation-fail-closed.mjs` Check 3 |
| Market-maker-bound capability accepted without verifying the market maker's trust status | `aoc/capabilities/core/evaluateCapabilityAccess.ts` | `evaluateMarketMakerTrust` now denies with `MARKET_MAKER_TRUST_UNVERIFIABLE` when no registry is supplied, instead of returning `null` (pass) | Callers that never intend to bind market makers are unaffected; callers that do must now explicitly wire a registry | `enforcement/__tests__/evaluateCapabilityAccess.test.ts` |
| Cross-subject revocation (attacker revokes someone else's grant) | `ControlPlaneService.revokeGrant` | Optional `subject_id` on the input is validated against the stored grant's `subject_id`; mismatch throws `AccessRequestSubjectMismatchError` | Caller identity itself is not authenticated inside `ControlPlaneService` — that's the API-gateway/auth layer's job, out of scope for this sprint | `runtime/__tests__/controlPlaneRevocation.test.ts` — "subject_id mismatch blocks the revoke" |
| Evidence deletion / tampering | `ControlPlaneService.listRevocationEvidence` | Evidence is append-only (`this.revocationEvidence.push(...)`); no delete/update method exists on the class | No persistence — evidence does not survive a process restart; a real store needs to make this append-only guarantee durable | Structural: no delete API exists to test the absence of |
| Delayed revocation propagation to descendants (delegations, sub-grants) | N/A — no real delegation/sub-grant hierarchy exists in this repo today | Not addressed this sprint | High — this is the single largest gap versus ADR §12's "must invalidate ... relevant delegations ... execution grants" requirement, because there is nothing to cascade to yet | None — documented as next-sprint work in `13-final-verdict.md` |
